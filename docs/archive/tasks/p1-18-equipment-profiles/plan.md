# Plan: [P1-18] Equipment profile auto-detection

**Slug:** p1-18-equipment-profiles **Issue:** #26 **Date:** 2026-09-23
**Governing DDs:** DD-003 (`equipment_profiles` / `frames` / `sessions` / `master_frames` schema,
UUIDv7 + `updated_at`, "no hard delete in v1", the inert-NULL-UNIQUE lesson), DD-006 (equipment
split rule — the reason profile identity must be stable), DD-004 (Stage 3 lists "equipment
profile detection (pure functions in packages/core)"; Stage 4 wiring belongs to P1-18a), DD-008
(no Equipment page in v1.0 — inline confirmation only, built by P1-21/P1-22), DD-002 (layering,
typed IPC). ADR-004 (alter `equipment_profiles`, never recreate it). ADR-007 (every mechanical
criterion must name a production mutation that turns it red).
**Status:** READY_FOR_SPEC

## Summary

This slice gives AstroTracker a stable notion of "rig": pure functions in `packages/core` that
turn a frame's raw `TELESCOP`/`INSTRUME`/`FOCALLEN` values into a deterministic equipment
identity key, collapse a batch of frames into distinct candidate profiles, and propose (never
apply) consolidations of near-identical header strings such as `EdgeHD 8` vs `EdgeHD8`; plus the
`packages/db` repository operations that persist detected profiles idempotently, resolve identity
keys to live profile ids, list merge suggestions, and let the user confirm, rename, and merge
profiles — with the merge remembered so a rescan never resurrects a profile the user merged away
— and report usage hours per profile (sum of light-frame exposure). The operations are exposed
over typed IPC but no page consumes them yet: per DD-008 v1.0 has no Equipment workspace, and the
inline confirmation surfaces belong to P1-21/P1-22. Assigning `frames.equipment_profile_id`
during scans and persisting sessions is P1-18a (#125) — this slice provides the functions P1-18a
calls, and nothing in this slice calls them from the scan pipeline.

## Design

### What the real data says (grounding for every rule below)

Sampled 2,716 real FITS/XISF headers under `Astrotracker_test_data/AstroTracker/TestData`
(read-only) plus the `fixtures/` manifests:

| Observed values                                                                                                              | Consequence                                                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TELESCOP='Gme28'` (FITS, 1,842 files) and `'Gme28'` **with the quotes inside the value** (XISF)                             | The PixInsight XISF quote quirk reaches `frames.telescope_raw` verbatim. Wrapping quotes must be stripped before identity, or every master splits off its lights. |
| `FOCALLEN` written as `336.0`, `336.`, `336`, `335.`, `335`, and `335.88495` (plate-solved XISF)                             | Focal length needs rounding for identity, and a tolerance for suggestions.                                                                                        |
| Same `Gme28` + `ZWO ASI533MC Pro` at `FOCALLEN` 336 **and** 420                                                              | 420 → 336 is the 0.8× reducer on a 420 mm scope. DD-003 "(+rotator/reducer)": these are different optical trains, so different profiles, and never suggested.     |
| `WO Gt 71` + ASI533MC Pro @ 335 and `GT71` + `AP26CC` @ 336                                                                  | Real drift is not just whitespace: a vendor prefix and case differ. Different cameras here, so correctly not one profile.                                         |
| `Gme28` vs `WO Gt 71`, same camera and focal length                                                                          | Probably one physical scope under two names. No string rule can catch this — see Open Question 4.                                                                 |
| `TELESCOP == INSTRUME == 'DWARF mini'`, `FOCALLEN 7.`                                                                        | Smart telescope. The default name must not read "DWARF mini + DWARF mini", and a 7 mm focal length is valid.                                                      |
| Fixtures: darks/flats/bias with `INSTRUME` only; RAW files with camera only; SGPro light with `FOCALLEN 800` and one without | Camera-only identities are real. A null focal length next to a known one is a suggestion case, not an auto-merge.                                                 |
| Fixtures: `ZWO ASI2600MC Pro` vs `ZWO ASI2600MM Pro` on the same scope                                                       | One character apart, and a colour camera versus a mono one. Edit-distance fuzziness would suggest merging them, so it is rejected.                                |

### Identity (automatic, deterministic, no user involvement)

`equipmentIdentity({ telescopeRaw, cameraRaw, focalLength })` → `{ telescope, camera,
focalLengthMm, matchKey } | null`:

- **String normalization, representation artifacts only:** trim; strip one pair of wrapping
  single quotes (the XISF quirk, same rule as `normalizeImageType`); trim again; empty → `null`.
  Case and internal whitespace/punctuation are **preserved** — those are the drift the acceptance
  criterion says must be _suggested_, not silently merged (Open Question 3).
- **Focal length:** non-finite or ≤ 0 → `null`; otherwise rounded to the nearest whole mm
  (`335.88 → 336`, `335.4 → 335`).
- **No identity** when both telescope and camera normalize to `null` (focal length alone does not
  identify a rig) → `null`, meaning "no profile".
- **`matchKey`** is an unambiguous serialization of the three normalized components (for example,
  a JSON array `[telescope, camera, focalMm]`), never a delimiter join: a header string that
  contains the delimiter must not collide, and a NUL-style sentinel was already rejected once in
  P1-17 (`6f796e0`).

### Detection

`detectEquipmentProfiles(inputs[])` → one `DetectedProfile` per distinct `matchKey`, with
normalized telescope/camera, rounded focal length, a default name, and the count of input rows
that carried it. The output is deterministic: sorted by `matchKey`, with no dependence on input
order. `defaultProfileName()` gives `"<telescope> + <camera> @ <f> mm"`, dropping missing parts,
collapsing `telescope === camera` to one, and leaving out the `@ … mm` part when focal is null.

### Suggestions (never applied automatically)

`suggestProfileMerges(profiles[], config?)` → `MergeSuggestion[]`, each
`{ profileIds, recommendedSurvivorId, reason }`, where `reason` is a visible code
(`'canonical_name_match'`) in the style of DD-006's "visible reasons":

- **Canonical form** per component: case-folded, with every non-alphanumeric character removed
  (`EdgeHD 8`/`EdgeHD8` → `edgehd8`; `Sky-Watcher`/`SkyWatcher` → `skywatcher`). Two profiles are
  candidates when their telescope canonical forms are equal (both null counts as equal) **and**
  their camera canonical forms are equal (both null counts as equal). Canonical equality is an
  equivalence relation, so the groups are clean with no transitivity surprises.
- **Focal compatibility inside a canonical group:** cluster the non-null focal lengths. Adjacent
  sorted values within a relative tolerance (default 2%, configurable) share a cluster. A
  null-focal profile joins the cluster only when the group has **exactly one** focal cluster.
  With two or more (for example 336 and 420) the null-focal profile is ambiguous and is left out
  of every suggestion.
- A suggestion is emitted only for a cluster with ≥ 2 profiles **and** at least one member with
  `isUserConfirmed = false`. Confirming the profiles separately is how a user says "these really
  are different" (Open Question 5).
- Merged-away profiles (`mergedIntoId !== null`) are never input.
- `recommendedSurvivorId` is chosen as: a confirmed profile first, then highest light-frame usage,
  then the lexicographically smallest id. It is deterministic and stated so tests can pin it.
- Explicitly **not** suggested: `ASI2600MC Pro` vs `ASI2600MM Pro`, `ASI294MC` vs `ASI294MC Pro`,
  336 mm vs 420 mm, a full-train profile vs a camera-only profile, or `WO Gt 71` vs `GT71`
  (vendor prefix). No edit-distance tier (Open Question 4).

### Persistence model (Open Question 1)

- `equipment_profiles.match_key`: the identity key of the row that detection created. There is a
  **partial** unique index `WHERE match_key IS NOT NULL`, because a composite UNIQUE over
  nullable components is inert in SQLite (NULLs are distinct). That is the exact defect DD-003
  records for `project_inputs`.
- `equipment_profiles.merged_into_id`: set on the loser when a merge happens. The row is kept,
  consistent with DD-003's "v1 does not hard-delete catalog rows", so that its `match_key` keeps
  resolving to the survivor on every future rescan. Invariant: `merged_into_id` always points at
  a **live** row (merges flatten chains), so resolution is one hop.
- Detection **inserts only**. It never updates an existing row's `name`, `telescope`, `camera`,
  `focal_length`, `is_user_confirmed`, or `merged_into_id`, so user renames and merges survive
  every rescan by construction.

### Repository surface (`EquipmentProfilesRepository`, extends CRUD)

- `detectFromFrames()`: reads the `SELECT DISTINCT telescope_raw, camera_raw, focal_length` rows
  from `frames` (set-based and cheap, covering all frame types), runs the core detection, and
  inserts a row for each `matchKey` that has no row yet (with `is_user_confirmed = false` and the
  default name). Returns `{ inserted, existing }` counts. Idempotent. It does **not** write
  `frames.equipment_profile_id` (P1-18a).
- `resolveMatchKeys(keys[])` → `Map<matchKey, liveProfileId>`, following `merged_into_id`. This
  is the seam P1-18a calls to assign frames.
- `listLive()`: live profiles (not merged) with `lightExposureSeconds`, `usageHours`, and
  `lightFrameCount` from a single GROUP BY query, never N+1.
- `usageHours(profileId)`: the same figure for one profile.
- `listMergeSuggestions()`: loads the live profiles plus their usage and calls
  `suggestProfileMerges`.
- `confirm(id)`: sets `is_user_confirmed = true` and re-stamps `updated_at`. Rejects a merged or
  unknown id.
- `rename(id, name)`: trims the name and rejects an empty result. Changes `name` only. Rejects a
  merged or unknown id.
- `merge(survivorId, mergedIds[])`: **one transaction**. It repoints
  `frames.equipment_profile_id`, `sessions.equipment_profile_id`, and
  `master_frames.equipment_profile_id` from every merged id to the survivor, re-stamping
  `updated_at` on each touched row (Phase-2 sync). It sets `merged_into_id = survivor` on the
  merged rows, flattens any rows previously merged into them, and marks the survivor
  `is_user_confirmed = true`. It rejects: survivor listed among the merged ids, an empty list,
  unknown ids, a survivor that is itself merged, or a merged id that is already merged. On
  rejection nothing changes.

### Usage hours (Open Question 6)

Usage for a profile is `Σ exposure_seconds` over `frames` with `frame_type = 'light'` and
`equipment_profile_id = profile`, then ÷ 3600 for hours. Frames whose file is `missing` count
(DD-003: stats stay stable when drives are offline; P1-13 uses the same rule). Frames whose file
is `duplicate` do not count, so a copy cannot double-count. A null `exposure_seconds` contributes 0. Seconds are returned alongside hours so the renderer can format `HHh MMm` (DD-008) without
float drift.

### IPC (Open Question 8)

The new channels are `equipment.list`, `equipment.suggestions`, `equipment.confirm`,
`equipment.rename`, and `equipment.merge`, and each needs an entry in `IPC_CHANNELS`, the
`IpcContract` map, and the exhaustive `IpcHandlers`. Their record types are local
(import-free), like `WatchFolderRecord`. Every input is validated in `register.ts` in the same
style as the existing validators (non-empty string ids, a non-empty id array, a non-empty trimmed
name). There is no `equipment.detect` channel, because detection is pipeline work (P1-18a). No
renderer code is added.

## Implementation Steps

### Step 7 — Repository: confirm, rename, merge

## Falsifiability notes for the Spec Writer (ADR-007)

These are the properties most likely to be tested vacuously, each paired with a mutation that
must turn its test red:

- **"Merged only on user confirm."** A test asserting only that `merge` was not called is blind.
  Assert on the data instead: frames keep their original profile id while a suggestion is
  pending. _Fails under:_ make `listMergeSuggestions()` (or `detectFromFrames()`) apply its first
  suggestion via `merge`.
- **"Suggested as one profile."** _Fails under:_ removing the whitespace-stripping from the
  canonical form. The test also needs the negative cases, or it passes under a rule that suggests
  everything. _Fails under:_ replacing canonical equality with `true` (MC vs MM must go red).
- **Identity keeps drift separate.** _Fails under:_ adding case-folding or internal-whitespace
  removal to `equipmentIdentity`. The `EdgeHD 8`/`EdgeHD8` two-key assertion must go red.
- **Rescan does not resurrect merged profiles.** _Fails under:_ making `resolveMatchKeys` ignore
  `merged_into_id`, or making `detectFromFrames` treat merged rows as absent.
- **Renames survive re-detection.** _Fails under:_ switching detection to upsert
  (`ON CONFLICT DO UPDATE SET name = …`).
- **Usage hours count lights only.** _Fails under:_ dropping the `frame_type = 'light'` predicate.
  The seeded dark and flat rows must carry non-zero exposure, or this mutation survives.
- **Merge atomicity.** _Fails under:_ removing the transaction wrapper and throwing after the
  frames repoint.
- **Partial unique index.** _Fails under:_ dropping the `WHERE` clause (two null-key rows must go
  red) or dropping the index (duplicate non-null keys must go red).

## Edge Cases

- **XISF quote quirk:** `telescope_raw = "'Gme28'"` (literal quotes) on PixInsight masters vs
  `'Gme28'` on FITS lights must be one identity. Strip exactly one wrapping pair, so a value
  consisting of just `''` becomes null, while a value with an unbalanced leading quote is kept
  verbatim.
- **FITS trailing-space padding** is already trimmed by the parser, but identity must trim again
  because the XISF and RAW paths do not.
- **FOCALLEN formats** `336.`, `336.0`, `336`, and plate-solved `335.88495` all mean 336. Values
  of 0, negative, NaN, or Infinity (some software writes 0 for "unknown") become null, not a
  0 mm profile.
- **Rounding boundary:** 335.5 rounds to 336. Whatever rule is used, 335.49 and 335.5 must be
  deterministic, and the 2% suggestion tolerance keeps them in one suggestion group anyway.
- **Reducer vs rounding:** 336 vs 420 on the same strings is two profiles and is **never**
  suggested (a 25% difference). 335 vs 336 is two profiles and **is** suggested.
- **Null focal next to known focal:** the SGPro fixtures have RC8 + QHY268M @ 800 and @ null. The
  null one is suggested only when the canonical group has a single focal cluster. With 336 and
  420 both present, it is ambiguous and left out rather than guessed.
- **Camera-only identities:** darks, bias, and DSLR RAW frames with no `TELESCOP` produce
  camera-only profiles, which are never suggested against a full-train profile. This is a
  cross-slice hazard for P1-18a and P1-17: DD-006's equipment split would make a night's darks a
  separate calibration-only session unless P1-18a attaches them. That resolution belongs to
  P1-18a (see Open Question 7), not here.
- **Telescope equals camera** (`DWARF mini`): the default name is not duplicated, and 7 mm focal
  is valid.
- **Colour vs mono twins** (`ASI2600MC Pro` / `ASI2600MM Pro`) and **suffix variants**
  (`ASI294MC` / `ASI294MC Pro`) are one character or one token apart and are different cameras.
  They must not be suggested.
- **Vendor-prefix drift** (`WO Gt 71` vs `GT71`) is not caught by canonical equality. This is
  accepted for v1 (Open Question 4).
- **Delimiter or sentinel collisions:** a header string containing `|`, `,`, `"`, or `]` must not
  produce the same `matchKey` as a different triple.
- **Pre-existing rows with null `match_key`** (none are created by v1 code, but 0000 allowed
  them): detection must not choke on them, and they are never resolved by key.
- **Merge chains:** A into B, then B into C, must leave A pointing at C. Merging into a merged
  survivor, merging a profile into itself, and re-merging an already-merged id are all rejected.
- **Merge touching sessions:** after repointing, two sessions on the same night can now share a
  profile. Re-running `detectSessions()` to collapse them is P1-18a's re-grouping, not this
  merge. The merge must not delete or rewrite sessions beyond the FK repoint, so notes survive.
- **Merge with locked sessions:** repointing `sessions.equipment_profile_id` must not touch
  `frames.session_id` or `session_assignment_locked`.
- **`updated_at` on repointed rows** must advance (Phase-2 sync keys off it). A bulk
  `UPDATE … SET equipment_profile_id` that forgets `updated_at` is a silent sync bug.
- **Usage hours with a `missing` drive** stay stable (counted). A `duplicate` file is not
  double-counted. A null exposure contributes 0, not NaN.
- **Rename to a whitespace-only name** is rejected. Duplicate names across profiles are allowed
  (names are labels, not identity).
- **Migration-number collision:** P1-20 is core-only, but P1-21 (which alters `master_frames`)
  and P1-12/P1-12a may also generate migrations on parallel branches. Whichever merges second
  must regenerate and renumber, not hand-edit, the snapshot chain.

## Invariant Checklist

- [ ] Non-destructive: no code path writes, moves, renames, or deletes user image files. Every
      operation touches catalog rows only, and "merge" means repointing foreign keys.
- [ ] Layering: identity, detection, and suggestion live in `packages/core/src/catalog/equipment`
      as pure functions over plain data (no fs, no Electron, no DB). SQL lives only in `packages/db`,
      and the renderer is untouched.
- [ ] DB: the altered table keeps its UUIDv7 PK and `updated_at`. The new columns come in through
      Drizzle migration 0008 with a round-trip test. Every repository write, including bulk
      repointing, re-stamps `updated_at`.
- [ ] Timestamps stored UTC (only audit timestamps are touched, via the existing helpers).
- [ ] Long-running work goes through the worker job queue. Nothing here runs in the scan path yet

## Open Questions

> **Resolved 2026-09-23 by the maintainer.** Decisions recorded on #26 (comment "Open Questions resolved"). Every recommendation below was accepted as written; treat them as settled.

1. **How a merge is remembered.** A rescan must not recreate a profile the user merged away.
   - **Recommended:** add `merged_into_id` on the merged-away row and keep the row (as specified
     above). It alters columns only, fits DD-003's no-hard-delete stance, and gives Phase 2 a
     natural tombstone.
   - _Alternative A:_ a new `equipment_profile_aliases(match_key → profile_id)` table, like
     `target_aliases`. It is cleaner for many-keys-per-profile, but adds a table DD-003 doesn't
     list.
   - _Alternative B:_ hard-delete the loser with no mapping. Rejected: the next rescan
     resurrects it.
2. **DD-003 text sync.** Should this PR update DD-003's `equipment_profiles` listing (`match_key`,
   `merged_into_id`) and its index list (`frames(equipment_profile_id)`)?
   - **Recommended:** yes, in the same PR, following the P1-17 precedent (P1-17 edited the DD-003
     listing for its 0007 columns) and ADR-004's drift lesson.
   - _Alternative:_ a separate docs PR.
3. **Where automatic identity stops and suggestion starts.**
   - **Recommended:** automatic handling only for representation artifacts: trim, one pair of
     wrapping quotes, and FOCALLEN rounded to whole mm (with ≤ 0 or non-finite treated as null).
     Case and internal whitespace or punctuation differences are suggestion-only. This is the
     literal reading of "merged only on user confirm".
   - _Alternative:_ also case-fold automatically. This means fewer suggestions, but `WO Gt 71`
     and `wo gt 71` would merge without the user seeing it.
4. **How fuzzy "fuzzy" is.**
   - **Recommended:** canonical-form equality only (case-folded, non-alphanumerics removed) plus a
     2% focal tolerance. No edit distance, because it would pair `ASI2600MC`/`ASI2600MM` and other
     model numbers that differ by one character. No vendor-prefix table.
   - _Alternative A:_ add a curated vendor-prefix table (WO, ZWO, Sky-Watcher…) so `WO Gt 71` ~
     `GT71` is suggested.
   - _Alternative B:_ add a lower-confidence "same camera + same focal length, different
     telescope string" suggestion. Real data shows exactly this (`Gme28` vs `WO Gt 71`, both
     ASI533MC Pro at ~336 mm, very likely one scope). It is valuable, but broader than the issue's
     "near-identical strings".
   - Recommend deferring both alternatives to the v1.x Equipment workspace.
5. **Dismissing a suggestion.**
   - **Recommended:** no new table. A suggestion group is suppressed once every member is
     user-confirmed, so "confirm both" means "these are different".
   - _Alternative:_ a persisted dismissal table (more precise, but it is new schema for a
     surface v1.0 barely shows).
6. **Usage-hours definition, and overlap with P1-13's per-equipment rollup.**
   - **Recommended:** count `light` frames only, include `missing` files (same as P1-13), and
     exclude `duplicate`-status files. P1-18 builds the per-profile query now, and P1-13 reuses
     it rather than writing a second one.
   - _Alternative:_ count duplicates too, for strict P1-13 parity, and let P1-13 decide duplicate
     handling for both.
7. **Frames with no `TELESCOP`** (darks, bias, DSLR RAW).
   - **Recommended:** they get distinct camera-only profiles. P1-18a decides how calibration
     frames attach to a night's light session, and #125's description should say so explicitly,
     because DD-006's equipment split otherwise turns every night's darks into their own session.
   - _Alternative:_ exclude non-light/non-flat frames from detection entirely (no profile for
     darks or bias). That is simpler, but loses the camera identity that DD-006 dark matching
     keys on.
8. **IPC channels with no consumer yet.**
   - **Recommended:** add the five `equipment.*` channels now, because the issue text says
     "exposed through the repository/IPC layer" and P1-21/P1-22 then only consume them.
   - _Alternative:_ repository only, with the channels added by the first UI slice that needs
     them.
