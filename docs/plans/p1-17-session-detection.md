# Plan: [P1-17] Session detection algorithm

**Slug:** p1-17-session-detection **Issue:** #25 **Date:** 2026-09-13
**Governing DDs:** DD-006 (session detection rules — primary), DD-003 (schema: `sessions`/
`watch_folders`/`frames` columns, timezone source, UUIDv7+`updated_at`), DD-002 (layering:
`packages/core` purity), ADR-004 (why `sessions`/`frames`/`watch_folders` already exist and must
be altered, not recreated)
**Status:** READY_FOR_SPEC

## Summary

This issue adds a pure function, `detectSessions()`, to `packages/core/catalog` that groups
parsed frames into imaging-night sessions per DD-006: local noon-to-noon astronomical-day
windowing, >4h gap splitting within a night, equipment-profile splitting, calibration-only
sessions, and — the two properties the whole design turns on — idempotent re-runs and respect
for explicit manual-assignment locks so that a user's merge/split survives the next scan. It
also alters the already-existing `sessions`, `watch_folders`, and `frames` tables (migration
0000, per ADR-004) with the minimal columns this algorithm and its tests actually require: an
IANA timezone on `watch_folders` (the DD-003 "site" timezone source) and on `sessions` (frozen
at detection time), a `timezone_source` audit column, and a per-frame manual lock flag. No
scan-pipeline wiring, no repository/IPC methods beyond the schema change, and no UI are in scope
— those are P1-19's job, which explicitly depends on this issue.

## The timezone model (stated precisely, per instruction)

**Where "site timezone" comes from.** DD-003's "Timezone source" note is explicit and this plan
follows it literally: `watch_folders.timezone` is the IANA timezone for astronomical-day
grouping, user-confirmable, one per watch folder. There is no dedicated multi-property "Site"
entity in v1 (lat/lon/Bortle site management is a later Phase-1.x backlog item —
`planning/task-breakdown.md` line ~666 — not part of this issue); for P1-17, "site" reduces
exactly to "the watch folder that owns this frame's file," reached via `frames.fileId →
files.watchFolderId → watchFolders.timezone`. `detectSessions()` itself does not perform this
join — it is a pure function over already-assembled `SessionInputFrame` records, and the DB join
is the impure caller's job (packages/db repository code or the future P1-19 orchestration layer,
neither built in this issue).

**Where "system timezone" comes from, and why it cannot be read inside `packages/core`.**
DD-006 says an unknown watch-folder timezone should "default to the system timezone." Node's
`Intl.DateTimeFormat().resolvedOptions().timeZone` reads the host machine's configured zone —
reading it _inside_ `detectSessions()` would make a function DD-006 itself calls "pure" produce
different results on different machines/CI runners for byte-identical input, which is not
testable and not actually pure. Resolution (DD-002 rule 1 supports this directly: effects belong
at the edges, `packages/core` stays pure): the caller resolves the system timezone once, at the
call site, and passes it in as `config.fallbackTimezone: string`. `packages/core` never touches
`Intl.DateTimeFormat` with no explicit `timeZone` argument, never reads `process.env`, and never
calls `resolvedOptions()`.

**The astronomical-day boundary rule, exactly.** DD-006: "a frame belongs to the session dated
by local noon-to-noon window (a 01:30 frame on Jul 6 belongs to the Jul 5 session)." Implemented
as: `label = localCalendarDate(instant - 12h, timezone)` — subtract 12 real hours from the UTC
instant, then take the local calendar date of the _shifted_ instant in the target IANA zone via
`Intl.DateTimeFormat('en-CA', { timeZone, year, month, day })`. This is correct across DST
transitions by construction: ICU resolves the correct UTC offset for whatever the _shifted_
instant is, so no manual DST special-casing is needed. Verified directly against Node 26 (this
repo's pinned engine, full-ICU by default since Node 13) for the DD-006 example itself, a
DST-spring-forward-adjacent instant, and a fractional UTC+5:30 offset (Asia/Kolkata) — all three
produce the expected calendar-date label. `astronomicalDayLabel()` is the only place
`packages/core` touches `Intl`.

**Per-frame resolution order** (implemented by `detectSessions()`, not by the caller): for a
frame with no prior session assignment, `effectiveTimezone = isValidIana(frame.watchFolderTimezone)
? frame.watchFolderTimezone : config.fallbackTimezone`, and `timezoneSource` is `'watch_folder'`
or `'system_fallback'` accordingly. `isValidIana` is implemented as
`try { new Intl.DateTimeFormat(undefined, { timeZone: tz }); return true } catch { return false }`
— confirmed to throw `RangeError` for a bogus zone string on Node 26.

**DD-003's stability requirement — and why it is an algorithm rule, not just a "don't overwrite
the column" rule.** DD-003: "`sessions.timezone` captures the timezone used at detection time so
historical grouping remains stable if settings change." Read literally ("detection time"), this
constrains `detectSessions()` itself: if it re-derived every frame's timezone from the _current_
`watch_folders.timezone` on every re-run, then editing a site's timezone setting later would
silently reshuffle which calendar-date bucket old, already-sessioned frames fall into on the next
routine rescan — exactly the instability DD-003 rules out. So: for a frame that already carries a
prior session assignment (`existingSessionId` non-null, with a recorded
`existingSessionTimezone`/`existingSessionTimezoneSource`), `detectSessions()` uses that frozen
value for the date-label computation, never the frame's current `watchFolderTimezone`. Only a
frame with no prior assignment resolves timezone fresh. (Frame _grouping_ — which session a
previously-unlocked frame ends up in — can still change on a re-run per the gap/equipment rules;
only the _timezone used to compute its date label_ is frozen once an assignment exists.)

**Timezone edge test (the acceptance criterion named explicitly).** Three sub-cases, same
physical instant `2026-07-06T00:30:00Z` where relevant:

1. Watch-folder timezone `'America/Denver'` (site tz, MDT UTC-6 in July) → local time
   `2026-07-05T18:30` (evening, ≥ noon) → `sessionDate = '2026-07-05'`, `timezoneSource =
'watch_folder'`.
2. Same instant, watch-folder timezone unset (`null`), `config.fallbackTimezone =
'Pacific/Auckland'` (deliberately far from the site, standing in for "whatever the analyst's
   OS happens to be set to") → local time `2026-07-06T12:30` (≥ noon) → **`sessionDate =
'2026-07-06'`** — a different calendar date than sub-case 1 for the _identical_ UTC instant.
   This is the concrete proof that site-vs-system timezone is not cosmetic: an unconfigured
   watch folder can silently mis-bucket a frame into the wrong night if the analyst's machine
   timezone differs from the site. `timezoneSource = 'system_fallback'` is asserted so the UI
   can eventually flag it (DD-006: "flag it as user-confirmable" — the confirming UI itself is
   out of scope here, but the flag this issue produces is what a later Settings/Sessions-page
   issue would surface).
3. A frame with `existingSessionId` set and `existingSessionTimezone = 'America/Denver'` (frozen
   from an earlier run), but whose _current_ `watchFolderTimezone` has since been changed to
   `'UTC'` by the user — asserts the output still uses `'America/Denver'`/`'watch_folder'`,
   proving the DD-003 stability rule above.

## Manual-assignment locks — concretely

**What is locked, and where it lives.** The lock is per-_frame_, not per-session:
`frames.session_assignment_locked` (new boolean column, default `false`). A locked frame's
`sessionId` is authoritative and `detectSessions()` never reassigns it, regardless of what the
astronomical-day/gap/equipment rules would independently compute. This is the one primitive that
composes into both edit types DD-006 names:

- **Merge** (two auto-detected sessions the user considers one night): the persisted result — not
  built in this issue — is "every frame from both original sessions now shares one `sessionId`,
  and every one of those frames has `session_assignment_locked = true`."
- **Split** (one auto-detected session the user divides at a chosen frame boundary): the
  persisted result is "the two frame subsets each keep/get a distinct `sessionId`, and every
  frame on both sides has `session_assignment_locked = true`."

`detectSessions()`'s contract given this: partition input frames into _locked_ and _unlocked_.
Locked frames are grouped by their existing `sessionId` verbatim (their membership is never
recomputed — they are "frozen islands"); only their derived boundary metadata (`startedAtUtc`,
`endedAtUtc`, `isCalibrationOnly`) is recomputed from whichever locked frames currently share that
id. Unlocked frames are re-grouped from scratch every run via the standard windowing/gap/equipment
rules (see below), which is what makes a locked group's split/merge survive: the algorithm simply
never looks at gap width or equipment profile for a locked frame — the gap/equipment rule that
would otherwise re-split a merge or re-join a split is not evaluated for members of a lock at all.

**Session identity across re-runs (needed for idempotency).** For a computed _unlocked_ group,
`SessionAssignment.sessionId` is chosen deterministically: if every member frame shares one
non-null `existingSessionId`, reuse it (nothing structurally changed, stable identity). If
members disagree (e.g. a new frame temporally bridges two previously-separate unlocked
auto-sessions, so the algorithm now legitimately merges them on its own), reuse the
**majority** `existingSessionId`, tying broken by the lexicographically smallest id (UUIDv7 sorts
chronologically, so this is also "the oldest surviving session wins" — deterministic and
stated explicitly for the test suite). If no member has a prior id, emit `sessionId: null` — the
(out-of-scope) persistence layer mints a fresh UUIDv7 row for a genuinely new group.

**Notes/weather notes need no lock.** `detectSessions()` never reads or writes
`sessions.notes`/`weatherNotes` — they are plain user-edited columns untouched by this function
entirely, so DD-006's "merge/split/notes... preserved via explicit assignment locks" phrase, for
the _notes_ part, is satisfied trivially by this function doing nothing to that column. (The
_persistence_ layer that applies `SessionAssignment[]` to the DB must `UPDATE` an existing session
row rather than delete-and-reinsert it when reusing an id, so notes physically survive — that
requirement is noted here for whoever builds it, P1-19, but is not testable inside this issue
since no such persistence code exists yet.)

## `detectSessions()` — algorithm

```ts
export type TimezoneSource = 'watch_folder' | 'system_fallback';

export interface SessionInputFrame {
  id: string;
  dateObsUtc: Date | null; // null = unparseable DATE-OBS; excluded from output
  equipmentProfileId: string | null;
  frameType: FrameType; // re-exported from ../classification/types.js
  watchFolderTimezone: string | null; // current watch_folders.timezone for this frame's file
  existingSessionId: string | null; // current frames.session_id
  existingSessionTimezone: string | null; // current sessions.timezone for that id
  existingSessionTimezoneSource: TimezoneSource | null;
  sessionAssignmentLocked: boolean; // current frames.session_assignment_locked
}

export interface SessionDetectionConfig {
  gapHours?: number; // default 4, per DD-006 ("configurable")
  fallbackTimezone: string; // caller-resolved system default; must itself be a valid IANA zone
}

export interface SessionAssignment {
  sessionId: string | null; // existing id to reuse, or null = mint new (caller's job)
  frameIds: string[];
  sessionDate: string; // YYYY-MM-DD local astronomical-day label
  timezone: string;
  timezoneSource: TimezoneSource;
  equipmentProfileId: string | null;
  startedAtUtc: Date;
  endedAtUtc: Date;
  isCalibrationOnly: boolean; // true iff no member frame has frameType === 'light'
}

export function detectSessions(
  frames: SessionInputFrame[],
  config: SessionDetectionConfig,
): SessionAssignment[];
```

Pseudocode:

```
detectSessions(frames, config):
  assert isValidIana(config.fallbackTimezone)   // caller misconfiguration -> throw
  usable = frames.filter(f => f.dateObsUtc !== null)   // unparseable DATE-OBS: excluded

  locked, unlocked = partition(usable, f => f.sessionAssignmentLocked && f.existingSessionId !== null)
  // a locked frame with no existingSessionId is a data-integrity gap; treat as unlocked

  lockedGroups = groupBy(locked, f => f.existingSessionId)
    -> for each group: resolve timezone/source from the earliest-dateObsUtc member's
       existingSessionTimezone/-Source (falling back to fresh resolution only if absent —
       a defensive case that should not occur in a healthy DB); emit as-is.

  for each unlocked frame, compute:
    effectiveTz, effectiveSource =
      f.existingSessionId && f.existingSessionTimezone
        ? (f.existingSessionTimezone, f.existingSessionTimezoneSource)   // DD-003 stability
        : isValidIana(f.watchFolderTimezone)
          ? (f.watchFolderTimezone, 'watch_folder')
          : (config.fallbackTimezone, 'system_fallback')
    sessionDateLabel = astronomicalDayLabel(f.dateObsUtc, effectiveTz)

  buckets = groupBy(unlocked, f => `${f.equipmentProfileId ?? '\0none'}|${sessionDateLabel(f)}`)
  for each bucket:
    runs = splitByGap(sortByDateObsUtc(bucket), config.gapHours ?? 4)
    for each run:
      sessionId = chooseSessionId(run)   // majority existingSessionId, tie -> smallest id, else null
      timezone/source = effectiveTz/effectiveSource of run's earliest-dateObsUtc member
      emit SessionAssignment{ sessionId, frameIds: run.ids, sessionDate: bucket's date label,
        timezone, timezoneSource: source, equipmentProfileId: bucket's profile,
        startedAtUtc: min(dateObsUtc), endedAtUtc: max(dateObsUtc),
        isCalibrationOnly: run.every(f => f.frameType !== 'light') }

  return [...lockedGroupAssignments, ...unlockedRunAssignments]
```

`splitByGap(sorted, gapHours)`: consecutive-pair difference on `dateObsUtc` epoch ms; a gap
**strictly greater than** `gapHours` hours starts a new run (exactly `gapHours` does not split —
DD-006's literal "> 4h").

## Test Plan (table-driven, `detect-sessions.test.ts` unless noted)

Per the issue's acceptance criteria, plus the timezone/lock rigor this plan adds:

1. **Midnight-spanning night** — frames 20:00 local–02:00 local (Jul 5→6, `America/Denver`), one
   equipment profile, gaps < 4h → one `SessionAssignment`, `sessionDate = '2026-07-05'`.
2. **Two-run night** — same night/profile, evening run + a >4h cloud gap + pre-dawn run → two
   `SessionAssignment`s, same `sessionDate`, split by the gap.
3. **Multi-rig night** — same night/time window, two distinct `equipmentProfileId`s, no time
   gap → two `SessionAssignment`s, split by equipment alone.
4. **DSLR without CCD-TEMP** — frames with no temperature-like field present at all (confirms
   `SessionInputFrame` has no such field and grouping doesn't implicitly depend on one) → normal
   single-session grouping, no crash.
5. **Calibration-only night** — all frames `frameType ∈ {dark,flat,bias,darkflat}`, one
   profile, no gap → one `SessionAssignment` with `isCalibrationOnly: true`.
6. **Timezone edge (site vs system tz)** — the three sub-cases under "Timezone edge test" above.
7. **Manual merge preserved** — two originally-separate runs (>4h gap) whose frames all carry
   `existingSessionId = 'session-A'` and `sessionAssignmentLocked = true` (simulating a
   user-applied merge); a rescan adds one new _unlocked_ frame temporally inside the old gap →
   asserts the four locked frames stay together as one `SessionAssignment` under `'session-A'`
   with boundaries computed only from themselves, and the new unlocked frame is emitted as its
   own separate assignment (does not silently get absorbed — see Open Questions).
8. **Manual split preserved** — four frames with no natural gap (<4h throughout) but
   `existingSessionId`/`sessionAssignmentLocked` already split 2+2 across `'session-X'`/
   `'session-Y'` (simulating a user-applied split) → asserts two `SessionAssignment`s reproducing
   exactly that split, even though gap logic alone would merge all four.
9. **Idempotency** — run `detectSessions()` once, mechanically apply its output back onto a copy
   of the input (`existingSessionId`/`existingSessionTimezone`/`existingSessionTimezoneSource` set
   per assignment), run again → byte-identical output (same `sessionId`s, same grouping) on the
   unchanged frame set.
10. **Session-id majority tie-break** — an unlocked bucket whose members carry two different
    non-null `existingSessionId`s (a new frame legitimately bridged two previously-separate
    auto-sessions) → asserts the majority id wins, and a 1-1 tie resolves to the
    lexicographically smaller id, deterministically.
11. **Exact-4-hour gap boundary** — gap of exactly 4h00m00.000s does not split; 4h00m00.001s
    does (also covered at the `splitByGap()` unit level in Step 4, re-asserted once through the
    full orchestrator).
12. **Frame with unparseable `dateObsUtc: null`** — excluded from every `SessionAssignment`;
    does not appear in any `frameIds` array and does not crash the run.

No new `fixtures/` assets are added — `detectSessions()`'s tests operate on literal
`SessionInputFrame`-shaped objects, matching the established convention in
`packages/core/src/classification/*.test.ts` (already-parsed/normalized data, not raw
FITS/XISF/RAW bytes) rather than the binary-fixture convention used by the parsers themselves.

## Edge Cases

- Frame with `dateObsUtc: null` (unparseable `DATE-OBS`) — cannot be windowed at all; excluded
  from output. Surfacing such frames for user review is a later (Review Queue-adjacent) concern,
  not this issue's.
- A frame's `watchFolderTimezone` is a malformed/non-IANA string — treated identically to `null`
  (falls back to `config.fallbackTimezone`); never throws for one bad frame.
- `config.fallbackTimezone` itself is invalid — throws at call time; this is a caller
  configuration bug, not a per-frame data-quality issue, and should fail loudly rather than
  silently mislabel an entire batch.
- A locked frame's `existingSessionId` has no matching `existingSessionTimezone` (defensive:
  should not occur in a healthy DB, e.g. an orphaned reference) — falls through to fresh timezone
  resolution rather than crashing.
- A `sessionAssignmentLocked: true` frame with `existingSessionId: null` (a lock with nothing to
  lock to) — treated as unlocked; a lock is only meaningful relative to an existing session.
- Two locked frames sharing one `existingSessionId` but disagreeing on
  `existingSessionTimezone`/`Source` (a data-integrity inconsistency that should not arise from a
  correct persistence layer) — resolved by using the earliest-`dateObsUtc` member's recorded
  value, deterministically.
- A manually merged/locked session plus a brand-new unlocked frame that falls inside its old gap
  on a later rescan — does not auto-join the locked group by this plan's default (see Open
  Questions #1); it becomes its own new candidate assignment.
- All frames in a night share `equipmentProfileId: null` (P1-18 hasn't run yet, or no
  TELESCOP/INSTRUME header) — grouped together as one bucket, not fragmented one-frame-per-session.
- A session's member frames span a DST transition — gap-splitting uses raw UTC epoch deltas
  (DST-immune); only the calendar-date _label_ is timezone-aware, and that computation is
  verified DST-safe by construction (12-hour UTC shift, then ICU resolves the correct offset for
  the shifted instant).
- Frames from two different watch folders with inconsistent `timezone` settings land in the same
  physical night but different `sessionDate` buckets — treated as a user configuration issue
  (inconsistent site timezone across watch folders that are actually the same site), not silently
  auto-corrected.
- Exactly-`gapHours`-long gap does not split; the smallest possible over-threshold gap does.

## Invariant Checklist

- [x] Non-destructive: `detectSessions()` and its helpers are pure functions over their
      arguments; no filesystem access, no image writes, anywhere in `packages/core/src/catalog/`
- [x] Layering: lives entirely in `packages/core`, no Electron imports, no `fs`; the only
      "environment" touch is Node's built-in `Intl` with an explicit `timeZone` argument supplied
      by the caller — never an ambient/system read inside `packages/core`
- [x] DB: no new tables — `sessions`/`watch_folders`/`frames` (all already UUIDv7 + `updated_at`

      this same issue, per DD-003's rollout rule
- [x] Timestamps stored UTC: `startedAtUtc`/`endedAtUtc` are UTC `Date`s derived from
      `dateObsUtc`; `sessionDate` is explicitly a local-date _label_ (already documented in
      `schema/sessions.ts` as the stated exception to the UTC-timestamp rule, not a timestamp)
- [x] Long-running work through worker queue: N/A — `detectSessions()` is synchronous and
      allocation-light; wiring it into any actual job/queue execution is P1-19's concern, not
      built here
- [ ] Performance budgets (PRD §8.4): flagged, not benchmarked here — no wiring exists yet to

      should benchmark the full detect-and-persist path against the PRD §8.4 targets when it
      wires this in.

## Open Questions

1. **Does a new, unlocked frame that lands inside a manually merged/locked session's old gap (on
   a later rescan) auto-join that locked session, or always form its own separate candidate
   assignment?** DD-006 says manual merges/splits are "preserved," but is silent on how newly
   scanned, unlocked frames interact with an existing lock. This plan's default — new unlocked
   frames never auto-join a locked group; they are always grouped independently by the standard
   rules, so the worst case is an extra small session appearing next to the user's carefully
   merged one, never a silently broken lock — is the conservative, safe reading, but a different
   answer (auto-absorb same-night/same-equipment new frames into an adjacent locked session) is
   equally plausible and has real UX consequences for P1-19's Sessions page. Flagging for human
   confirmation rather than deciding silently, per the task instructions.
